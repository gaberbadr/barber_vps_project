1. ARCHITECTURE OVERVIEW & BLITZ.CLOUD CAPABILITIES
================================================================================
The project is organized as a multi-service Docker architecture deployed via
Blitz.cloud's GitHub integration and managed edge infrastructure:

- Ingress & TLS Termination:
  Managed directly by Blitz.cloud's edge router (edge.blitz.cloud).
  TLS/HTTPS certificates are issued and auto-renewed via Let's Encrypt at the edge.
  The containerized Nginx instance listens internally on HTTP port 80 and accepts
  forwarded HTTPS traffic without requiring local certificate files or in-container
  Certbot loops.

- Services:
  * barber-nginx (Nginx Alpine): Public-facing reverse proxy routing traffic to
    frontend (/), backend (/api/), swagger (/swagger/), uploads (/files/), and /health.
  * barber-frontend (React Vite SPA on Nginx): Production static SPA build.
  * barber-api (.NET 8 Web API): Business logic, EF Core, Identity, authentication.
  * barber-postgres (PostgreSQL 16 Alpine): Relational persistence.
  * barber-redis (Redis Alpine): In-memory cache & rate limiting with fallback.
  * barber-pgadmin (pgAdmin 4): Database management (isolated to loopback).

- Private Network:
  All services communicate over the internal Docker network "barber-network".
  PostgreSQL, Redis, Backend, and Frontend are not exposed to the public internet;
  only Nginx is exposed on port 80 to the Blitz.cloud edge router.

3. DNS CONFIGURATION (CUSTOM DOMAIN: barber.devs.surf)
================================================================================
Configure the following records in your DNS manager (Cloudflare, Namecheap, GoDaddy):

1. Primary Routing Record (CNAME):
   - Type: CNAME
   - Name: barber (or barber.devs.surf depending on DNS provider interface)
   - Target: edge.blitz.cloud
   - TTL: Auto or 3600
   * Cloudflare Notice: If using Cloudflare DNS, set the Proxy status to
     "DNS Only" (Grey Cloud) so Blitz.cloud can directly complete the ACME HTTP-01
     challenge for SSL certificate issuance.

2. Ownership Verification Record (TXT) (If required by Blitz.cloud):
   - Type: TXT
   - Name: _blitz-verify.barber
   - Value: <Copy verification token provided in Blitz.cloud Domains tab>
   - TTL: Auto or 3600

  Example: S3cur3_P0stgr3s_P@ssw0rd!

- ConnectionStrings__DefaultConnection (Secret)
  Purpose: ADO.NET connection string used by EF Core in .NET.
  Format: Host=db;Port=5432;Database=project1;Username=postgres;Password=S3cur3_P0stgr3s_P@ssw0rd!

- ConnectionStrings__REDIS_URL (Non-Secret)

6. SERVICE COMMUNICATIONS & NETWORKING
================================================================================
- Inbound Traffic Flow:
  1. Client sends request to https://barber.devs.surf/
  2. Blitz.cloud edge proxy terminates TLS, applies managed SSL certificate, and
     injects X-Forwarded-Proto: https, X-Forwarded-For, and Host headers.
  3. Blitz.cloud edge forwards request to barber-nginx container on port 80.
  4. Nginx inspects the request path:
     * /health    -> http://backend:8080/health (Backend health probe)
     * /api/*     -> http://backend:8080/api/* (Backend ASP.NET Core API)
     * /files/*   -> http://backend:8080/files/* (Static user uploads)
     * /swagger/* -> http://backend:8080/swagger/* (OpenAPI Documentation)
     * /*         -> http://frontend:80/* (React Vite SPA)
  5. The backend trusts X-Forwarded-Proto via UseForwardedHeaders middleware,
     avoiding conflicting redirect loops.

7. DATABASE MIGRATIONS & INITIAL DATABASE SETUP
================================================================================
Database lifecycle is completely automated inside the backend's startup pipeline:
1. Docker Compose healthcheck on "db" verifies PostgreSQL is healthy using:
   pg_isready -U postgres -d project1
2. The "backend" container waits until the database healthcheck is healthy before booting.
3. On application boot, Program.cs executes:
   - Database Migration: await context.Database.MigrateAsync() applies all pending
     EF Core migrations in sequential order.
   - Roles Seeding: DefaultRolesSeeder seeds required identity roles (Admin, Barber, Customer).
   - Admin Seeding: DefaultAdminSeeder seeds default system administrator credentials.
   - Data Seeding: DatabaseSeeder seeds working hours, initial services, coupons,
     and booking settings.
4. No manual migration commands or database initialization scripts are required.

8. PERSISTENT VOLUMES & DATA PRESERVATION
================================================================================
Data persists across container restarts, image rebuilds, and code pushes via
named Docker volumes declared in docker-compose.yml:

1. postgres_data (/var/lib/postgresql/data):
   Stores all relational database tables, identity accounts, bookings, and logs.
2. api_files (/app/wwwroot/files):
   Stores user-uploaded profile pictures, barber images, and service attachments.
3. redis_data (/data):
   Stores Redis state snapshots (if persistence is enabled).
4. pgadmin_data (/var/lib/pgadmin):
   Stores pgAdmin preferences, saved server connections, and query history.

Redeploying new commits to Blitz.cloud does NOT overwrite named volumes.
Your data remains intact across deployments.

- Ensure the React UI renders properly, CSS styles and images load without 404s.
- Navigate to client-side routes (e.g. /login, /about) to confirm SPA routing works.

Step 4: Verify API & Swagger Documentation
- Navigate to: https://barber.devs.surf/swagger

- Enter http://barber.devs.surf/ in the address bar.
- Confirm that the browser automatically upgrades to https://barber.devs.surf/
  without any redirect loops (ERR_TOO_MANY_REDIRECTS).

11. TROUBLESHOOTING GUIDE
================================================================================
1. Problem: "Secure connection is still being set up" / SSL Warning
   - Cause: DNS records were recently updated or ACME challenge is still validating.
   - Solution: Verify your CNAME record points to edge.blitz.cloud. If using
     Cloudflare, verify proxy mode is set to "DNS Only" (Grey Cloud). Allow up
     to 5 minutes for Let's Encrypt edge provisioning.

2. Problem: "ERR_TOO_MANY_REDIRECTS"
   - Cause: Nginx or ASP.NET Core redirecting HTTPS requests back to HTTPS.
   - Solution: Verify nginx.conf contains:
     map $http_x_forwarded_proto $forwarded_proto { default $http_x_forwarded_proto; '' $scheme; }
     proxy_set_header X-Forwarded-Proto $forwarded_proto;
     and that Nginx does not execute unconditional port 80 redirects.

3. Problem: Backend Container Fails Startup ("Starting...")
   - Cause: Database migration failure or unreached database.
   - Solution: Check Blitz.cloud Activity/Logs tab for "Startup.DatabaseInitialization".
     Ensure ConnectionStrings__DefaultConnection exactly matches DB_PASSWORD.

4. Problem: Redis Connection Warnings in Logs
   - Cause: Redis container booting slower than backend.
   - Solution: InfrastructureDependencyInjection.cs includes safe connection fallback.
     Rate limiting and caching automatically switch to thread-safe in-memory
     storage without crashing the application.

5. Problem: File Uploads Fail (HTTP 413 Payload Too Large)
   - Solution: Nginx has client_max_body_size set to 20M. Ensure individual
     uploads do not exceed 20 MB.

12. BACKUP, RECOVERY & MAINTENANCE
================================================================================
1. Database Dumps via Blitz.cloud:
   - On the Blitz.cloud dashboard, you can download a full PostgreSQL pg_dump
     snapshot directly under Databases -> "Download a copy".
   - You can also upload an existing .sql or .dump file when migrating data.

2. pgAdmin Management:
   - pgAdmin 4 is bound to 127.0.0.1:5050 for security.
   - If using a private network or SSH tunnel to the host:
     Login: Value of PGADMIN_DEFAULT_EMAIL
     Password: Value of PGADMIN_DEFAULT_PASSWORD
     Host: db (internal Docker network hostname)
     Port: 5432
     Database: project1
     User: postgres

3. Inactivity Sleep Behavior:
   - On free accounts, Blitz.cloud puts apps to sleep after 30 minutes of no traffic.
   - The first visitor will experience a 5-10 second cold start while the
     containers wake up. All subsequent requests respond instantly.
